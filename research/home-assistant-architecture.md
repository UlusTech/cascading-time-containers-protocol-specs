# Home Assistant architecture (prior art)

Scope note: this reports how Home Assistant (HA) works. It does not design CTCP. Line references below are to the checked-out 2026.9.4 tree under `homeassistant/`.

## Answer

1. **Core.** `HomeAssistant` (core.py:381) is a root object holding three primitives plus config: `hass.bus` (EventBus), `hass.states` (StateMachine), `hass.services` (ServiceRegistry; user-facing name "actions", class name unchanged). It also has `hass.data` (a free-for-all dict any component can write to), `hass.config`, and `hass.config_entries`. Everything domain-specific (lights, sensors, calendars, sun, MQTT, the automation engine itself, the HTTP API, websocket API) is an integration under `homeassistant/components/` (1509 directories in 2026.9.4).
2. **Integrations** are directories with `manifest.json` + `__init__.py` (minimum). Dependencies are declared in the manifest (data, not types) and resolved at runtime by the loader, with a separate static check (hassfest, CI only) for core integrations. Missing/circular `dependencies` make the integration fail to set up with a logged error; the rest of HA keeps running.
3. **Stability.** No frozen plugin API. Core and custom integrations use the same Python internals; stability is by written deprecation process (6 months user-facing, 12 months developer-facing) plus a deprecation-warning mechanism. Custom integrations only get warnings where core integrations get hard errors. Written policy (developers.home-assistant.io/docs/deprecating): 6 months minimum for user-facing removals, 12 months for developer-facing (custom-integration) removals, announced on the dev blog.
4. **Automations** = trigger(s) + optional condition(s) + action(s); scripts = action sequences callable by name; blueprints = parameterised automation/script/template-entity YAML with `!input`. Templating = sandboxed Jinja2 with HA extensions and a "limited" mode; known gaps include blueprint inputs not being template variables and triggers not accepting templates.
5. **APIs.** REST (`/api/...`, bearer token) and a WebSocket API (JSON messages with numeric ids). The frontend uses the WebSocket API primarily (and REST secondarily). Integrations add their own websocket commands.
6. **Instance to instance.** One legacy core integration, `mqtt_eventstream`, forwards events (JSON over an MQTT broker) between two instances and re-fires them with `EventOrigin.remote`; no other official HA-to-HA feature found. The community `remote_homeassistant` custom integration links instances via the websocket API and mirrors remote states locally and forwards service calls.
7. **Typing.** mypy, opt-in per module via `.strict-typing`; `ConfigEntry` is generic over `runtime_data`. No typing expresses inter-integration dependencies; the only dependency checking is the manifest lists plus an AST-import scan in hassfest.
8. **Failure modes.** Shared Python environment (pinned requirements conflicts), unstable internals breaking custom integrations, YAML/Jinja footguns, setup blocking, silent config removals. See section 8.

## Evidence

### 1. Core architecture

**Verified (code, 2026.9.4):**
- `HomeAssistant.__init__` (core.py:405-425) creates `self.data = HassDict()` ("a dictionary that any component can store any data on"), `self.bus = EventBus(self)`, `self.services = ServiceRegistry(self)`, `self.states = StateMachine(self.bus, self.loop)`, `self.config = Config(...)`. `auth`, `http`, `config_entries` are class attributes assigned later (core.py:384-386).
- **EventBus** (core.py:1506): `_listeners` is a `defaultdict` from event type (string or `EventType[T]`) to listener list, plus a `MATCH_ALL` list. `fire` is thread-safe via `call_soon_threadsafe`; `async_fire` must run on the loop. Event type length is capped (`MAX_LENGTH_EVENT_EVENT_TYPE = 64`, const.py:56). `Event` (core.py:1359) carries `event_type`, `data`, `origin`, `context`, `time_fired`. `EventOrigin` is `local | remote` (core.py:1341); tree-wide code search (GitHub code search on the dev branch, not the tag, 2026-09-30) finds production uses in `components/api` (REST `POST /api/events/<type>`, api/__init__.py:363), `components/mobile_app/webhook.py` (fire_event webhook, line ~318) and `components/mqtt_eventstream` (see section 6); the remaining hits are tests/recorder schemas.
- **Context** (core.py:1282): `id` (ULID), `user_id`, `parent_id`, `origin_event`. Passed through events, state changes and service calls (causality/attribution).
- **StateMachine** (core.py:2200): one `State` per `entity_id` (`domain.object_id`), holding state string + attributes. `async_set` writes and fires `state_changed` (`EVENT_STATE_CHANGED`, typed `EventType[EventStateChangedData]`, const.py:286) on the bus. Entity id cache is bounded (`MAX_EXPECTED_ENTITY_IDS = 16384`).
- **ServiceRegistry** (core.py:2620): `dict[domain, dict[service, Service]]`. `async_call` validates data against the registered schema, fires `call_service` on the bus (core.py:2943), then runs the handler; `blocking=False` returns immediately; `return_response=True` allows a JSON response (core.py:2860-2872).
- What core does not own: no light, sensor, calendar, time-of-day or scheduling concept in these three classes. The automation engine, scripts, blueprints, HTTP server, REST API, websocket API are all integrations (`components/automation`, `blueprint`, `api`, `websocket_api`). Some integrations are effectively mandatory: `CORE_INTEGRATIONS = {"homeassistant", "persistent_notification"}` (bootstrap.py:152), and bootstrap has staged startup lists (`STAGE_0/1/2`, bootstrap.py:145-215).

**Verified (docs):**
- `hass` object: `hass.states` "allows you to set states and track when they are changed", `hass.bus` "allows you to trigger and listen for events", `hass.services` "allows you to register service actions" (developers.home-assistant.io/docs/dev_101_hass). "The core of Home Assistant is driven by events" (dev_101_events). Event data must be JSON-serializable.
- Services vs actions: dev docs use "service actions"/"actions" interchangeably; "the underlying implementation remains service-based" (dev_101_services, paraphrase by fetch tool). Code names remain `ServiceRegistry`, `hass.services`, event `call_service`, REST `/api/services`. Docs say service actions "should always be registered [in `async_setup`] to ensure automations referencing them can be edited and validated"; integration-level (not per config entry) registration keeps them available with no loaded entries. Entity services use `async_register_platform_entity_service()`.

### 2. Integrations as plugins

**Verified (docs, creating_integration_file_structure / manifest):**
- Minimum: `manifest.json` (needs `domain`, `name`) and `__init__.py`. Optional: platform files (`light.py`, `sensor.py`), `services.yaml`, `coordinator.py`, `config_flow`, `strings.json`/translations, `brand/`.
- Lookup: `<config>/custom_components/<domain>` (custom) and `homeassistant/components/<domain>` (built-in). A custom directory may override a built-in one ("prevents receiving updates").
- Manifest fields (docs list): `domain, name, version, integration_type, documentation, issue_tracker, dependencies, after_dependencies, codeowners, config_flow, single_config_entry, requirements, loggers, quality_scale, iot_class`, discovery keys (`bluetooth, zeroconf, ssdp, homekit, mqtt, dhcp, usb`), and virtual-integration pointers `supported_by`/`iot_standards`. `import_executor` also exists in the loader (loader.py:~873). `integration_type` values in code: `entity, device, hardware, helper, hub, service, system, virtual`; default `hub` (loader.py:867-874). `version` is required for custom integrations only (AwesomeVersion-valid) and should be omitted for core. `quality_scale` bronze/silver/gold/platinum (plus `internal` used by e.g. `sun`).
- `dependencies`: "other Home Assistant integrations you want Home Assistant to set up successfully before the integration is loaded"; "does not guarantee all dependency configuration entries have been set up".
- `after_dependencies`: setup waits for the listed integrations to be set up first, if they are configured; their requirements are installed regardless. Example in docs: `camera` lists `stream`.
- `requirements`: pip strings (e.g. `pychromecast==3.2.0`) installed into a deps directory before import; "if steps fail... the component will fail to load".
- Restriction: built-in integrations may list only built-in integrations in `dependencies`/`after_dependencies`; custom ones may list both. "Custom integrations should only include requirements that are not required by the Core requirements.txt."
- Example manifest read from source: `components/sun/manifest.json` = `domain, name, codeowners, config_flow: true, documentation, integration_type: service, iot_class: calculated, quality_scale: internal, single_config_entry: true`.
- Config entries: persistent user-created config per integration; lifecycle states not loaded / loaded / setup error / setup retry / unload in progress; `async_setup_entry`, `async_unload_entry`, `async_migrate_entry`; entries must not be mutated directly (dev docs config_entries_index).

**Verified (code) load-order and failure behaviour:**
- Setup entry `async_setup_component` first calls `integration.resolve_dependencies()` ("Validate all dependencies exist and there are no circular dependencies", setup.py:326-328); if it returns None the setup returns False (integration not set up).
- `loader.resolve_integrations_dependencies` (loader.py:1505) recursively walks `dependencies` (and, with the default `possible_after_dependencies=None`, all `after_dependencies`). It tracks a `resolving` set; re-entry raises `CircularDependency` whose cycle list is extended on unwind (loader.py:1585-1650, 1676-1686). A dependency domain that cannot be found yields `IntegrationNotFound` (loader.py:1658). Errors are caught per integration in `_resolve_deps_catch_exceptions` and logged as `Unable to resolve (after) dependencies for <domain>: <exc>` (loader.py:1540-1548); that integration is then dropped. Bootstrap does the same for all configured domains up front: "Eliminate those without valid dependencies" (bootstrap.py:822-830).
- Actual ordering at setup: `_async_process_dependencies` (setup.py:193-260) creates/awaits setup tasks for each `dependencies` entry (starting it if not already started), and for `after_dependencies` only waits on those "in `to_be_loaded`" (i.e. configured to be set up in this run). It `asyncio.gather`s them; any that return False produce `Unable to set up dependencies of '<domain>'. Setup failed for dependencies: [...]` and `DependencyError`, so the dependent does not set up. 
- The dependency-wait is under `hass.timeout.async_freeze(domain)`, i.e. the setup timeout clock is paused while waiting on dependencies.
- Requirements are installed after dependency resolution and before import (setup.py:330-335; requirements.py). Skipping is possible with `hass --skip-pip-packages` (dev docs api_lib_index; requirements.py:257, 286).

**Verified (code) static checking:**
- `script/hassfest/dependencies.py` (CI tool for core; custom integration authors can run hassfest too, not verified here) parses each integration's Python files with `ast`, collects references to other integrations (`ImportCollector`), and reports `Using component <x> but it's not in 'dependencies' or 'after_dependencies'`. Also reports circular dependencies (including through `after_dependencies`), a domain being in both lists, and nonexistent dependency domains (dependencies.py:238-345). Exempt: `CORE_INTEGRATIONS`, an `IGNORE_VIOLATIONS` list.
- So: the manifest is data. The loader checks it at runtime; a separate lint step checks manifest vs actual imports in CI. Nothing in the Python type system links them.

**Inference (mine):** Load order looks emergent from asyncio awaiting rather than a computed topological sort: the only sort in `bootstrap.py`/`setup.py` is `sorted(domains, key=SETUP_ORDER_SORT_KEY)` where the key is `partial(contains, BASE_PLATFORMS)` (bootstrap.py:129, 1103), i.e. base platforms first; grep for `sort|topolog` in bootstrap.py and setup.py found nothing else (loader.py not grepped for sorting). Also, because `after_dependencies` is resolved with `possible_after_dependencies=None` in `resolve_dependencies()`, a nonexistent after_dependency domain appears to make resolution fail (dependency `Exception` is re-raised, loader.py:1614-1620), even though the docs describe after_dependencies as optional. I did not run HA to confirm; treat as unverified behaviour.

### 3. Plugin API stability

**Verified:**
- Core vs custom: same runtime API; differences are manifest constraints above (version required, dependencies restrictions), review/CI (core: hassfest, tests, `requirements_all.txt`, CODEOWNERS, Ruff, typing per `.strict-typing`; dev docs development_checklist), and the deprecation helper: `helpers/frame.report_usage(...)` defaults to `core_behavior=ReportBehavior.ERROR` and `custom_integration_behavior=ReportBehavior.LOG` (frame.py:~165-168). Same call site raises for a core integration and only logs for a custom one. `deprecated_function`/`deprecated_class`/deprecated constants take `breaks_in_ha_version` and log "It will be removed in HA Core X" (helpers/deprecation.py:89-250).
- Release cadence: monthly, first Wednesday, ~1 week beta; patch releases as needed (home-assistant.io/faq/release). Search-derived (not read at source): weekly Friday patch goal for 2026.9.
- **Written deprecation process** (https://developers.home-assistant.io/docs/deprecating, read 2026-09-30; linked from the development checklist sentence "Anything that removes or changes existing behavior follows the deprecation process"): required periods "Users (YAML, actions, entities, integrations): 6 months"; "Developers (constants, helpers, APIs for custom integrations): 12 months"; periods cannot be shortened but may be extended. User-facing deprecations get a repair issue (WARNING while old behaviour works, ERROR after removal); developer-facing ones get warning logs and "an announcement post on this site's blog naming the replacement if applicable and the removal version". Removals carry `breaks_in_ha_version` in calendar version form.
- Deprecation windows seen: ADR 0021 (2023-06-15, Accepted): YAML integration configuration deprecation "at least 6 months (being 6 release cycles at the time of writing)", requires migration/import where possible and a repair issue for users. Legacy template entities: deprecated 2025.12, removed 2026.6 (community thread by the integration author, 6 months). Developer-API items in the dev blog: `modbus.get_hub` deprecated 2026.10, removed 2027.10, "custom integrations that call it get a warning in the log until then, and stop working after that" (12 months, matching the written policy); `via_device` -> `via_device_id` needed before 2027.8 (secondary, from a third-party GitHub issue). The dev blog is the announcement channel (e.g. 2026-09-15 "DeviceEntry.config_entries deprecation is now enforced", 2026-08-31 "Configurator integration is now deprecated", removal 2027.10).
- A general "official deprecation policy" proposal (architecture issue #368, 2020) was closed as not planned. So: no single written policy for all API surfaces was found; ADR 0021 covers YAML config only. The 12-month developer period is stated policy (above) and consistent with the `modbus.get_hub` example. Gap: adherence across all changes was not audited; the process page says only that periods "may extend".
- HACS: "not official Home Assistant software — a community-developed custom integration" that discovers, downloads, updates/removes custom elements (integrations, themes, plugins, scripts) (hacs.xyz). It installs into `custom_components`. Its `hacs.json` format was not verified. Custom integrations are otherwise hand-copied.

**What breaks custom integrations (documented/observed):**
- Removed/changed internal Python APIs after deprecation windows (blog posts above).
- Requirement conflicts, since custom integrations share the core environment: home-assistant.io/faq/problems-with-dependencies says issues occur "when the custom integration has not yet been updated for a new Home Assistant release, or when it conflicts with another custom integration" (the page does not address core conflicts). GitHub issues corroborate (secondary: HACS issue #899, core issue #130829, HA 2022.3 undocumented breaking change home-assistant.io#21766; not individually read).
- Example from a live custom integration tracker: remote_homeassistant issues report "Setup failed for custom integration" after HA updates and asks "Does this work on HA 2026.8?" (issues page, fetch-tool summary; treat as indicative).

### 4. Automations

**Verified (docs and code):**
- Automation = triggers, optional conditions, actions. User YAML: `automation: triggers: - trigger: event ...` (home-assistant.io/docs/automation/trigger). Verified in code: a validator normalises the user key `trigger` to internal `platform` (`value[CONF_PLATFORM] = value.pop(CONF_TRIGGER)`, helpers/config_validation.py:~1847-1856; specifying both raises "Please use 'trigger' only"); the internal schema still uses `CONF_PLATFORM` (line 1861-1870). The release in which `trigger:` replaced `platform:` was not determined. Automation modes: `single, restart, queued, parallel` (helpers/script.py:116-119).
- Trigger types listed in docs (14): event, geolocation, homeassistant, mqtt, numeric_state, sentence, state, sun, tag, template, time_pattern, time, webhook, zone. Triggers are provided by integrations: `helpers/trigger.py` looks up the trigger platform by key, and a trigger platform implements `async_validate_trigger_config` and `async_attach_trigger(hass, config, action, trigger_info) -> CALLBACK_TYPE` (or newer `async_get_triggers`-based descriptors) (trigger.py:1356-1372, 1651-1672). Conditions and actions are extensible similarly (`helpers/condition.py`, `helpers/script.py`); action = call an action (service), delay, wait_template, wait_for_trigger, repeat, choose, if/then, parallel, variables, `response_variable`, `continue_on_error`, `enabled: false` (home-assistant.io/docs/scripts).
- Scripts: "a sequence of steps that Home Assistant runs from top to bottom whenever you call it"; run when called (from UI, other actions), automations run on triggers; same action syntax.
- Blueprints: "pre-configured automation, script, or template entity templates with customizable fields"; one blueprint can back many automations; automations built from a blueprint inherit blueprint updates (docs/blueprint). Schema: `blueprint: {name, domain (automation|script|template), description, author, homeassistant.min_version, input: {...}}`; inputs may have `default` and a `selector`; referenced by the `!input` YAML tag; input sections since 2024.6.0. Limit stated in docs: "The inputs are available as custom YAML tags, but not as template variables" (docs/blueprint/schema). `trigger_variables` exist so blueprint inputs can be used in triggers ("Trigger variables are a feature meant to support using blueprint inputs in triggers"), limited templates only.
- Templating: Jinja2 via `ImmutableSandboxedEnvironment` (helpers/template/__init__.py:786) plus ~20 HA extensions (state, area, device, math, regex, datetime, etc., lines 800-820). "Limited" templates cannot access functions (template docstring line ~387; asserts a template cannot switch between limited/non-limited or combine strict+limited). Output cap `MAX_TEMPLATE_OUTPUT = 256 KiB`. `RenderInfo` tracks which entities/domains a template read so it can re-render only on relevant `state_changed` (with rate limiting) (helpers/template/render_info.py).
- Documented limits and complaints: template triggers/blueprint triggers cannot contain Jinja (architecture discussion #1153, maintainer `frenck` "positive" but needing another core member's approval, as summarised by fetch tool); webhook_id templates evaluated only at trigger setup; "triggers will not re-apply if the value of the template changes". Community PSA on YAML-vs-Jinja confusion (search snippet only, not read).

### 5. APIs

**Verified (docs, 2026-09-30):**
- REST: same port as frontend (8123); `Authorization: Bearer TOKEN` (long-lived token from profile). Endpoints: `GET /api/`, `/api/config`, `/api/states`, `GET|POST|DELETE /api/states/<entity_id>`, `/api/services`, `POST /api/services/<domain>/<service>` (returns list of states that changed during execution; `?return_response` for response data, otherwise a 400 if the service must return data), `/api/events`, `POST /api/events/<event_type>`, `/api/history/period/`, `/api/logbook/`, `POST /api/template`. No explicit stability guarantee in the docs.
- WebSocket (`/api/websocket`): server sends `auth_required` (with HA version), client sends `auth` with token, server `auth_ok`/`auth_invalid`. Thereafter every message is JSON with `type` and a client-chosen increasing integer `id`; results `{id, type: "result", success, result|error{code,message}}`. Commands: `subscribe_events` (with optional event_type filter), `subscribe_trigger` (subscribe with automation-style trigger config), `call_service`, `get_states`, `get_config`, `get_services`, `get_panels`, `fire_event`, `ping`, plus `supported_features` (currently `coalesce_messages`). Integrations register their own commands with `@websocket_api.websocket_command(schema)` + `websocket_api.async_register_command(hass, handler)` (dev docs frontend/extending/websocket-api).
- **Contradiction, docs vs code:** the WebSocket docs page says `call_service` currently has "no return value". Code in 2026.9.4 (`components/websocket_api/commands.py:270-296`) accepts `return_response` (default false) and returns `response` in the result. Code is primary; the docs page is stale on this point.
- Frontend: "leverages the WebSocket API and the REST API"; data flows through a `hass` object (with the websocket `connection`) to Lit web components; subscriptions over websocket keep state in sync; custom panels call integration commands via `hass.connection.sendMessagePromise()` (dev docs frontend/architecture, extending/websocket-api). The JS client library name `home-assistant-js-websocket` was not verified in this session.
- Backpressure constants exist in websocket_api/const.py (`MAX_PENDING_MSG = 4096`, `PENDING_MSG_PEAK = 1024`, `PENDING_MSG_PEAK_TIME = 10`); semantics not read.

### 6. Instance to instance

- **A core, legacy-status mechanism exists: `mqtt_eventstream`** (`homeassistant/components/mqtt_eventstream`, module docstring "Connect two Home Assistant instances via MQTT"; manifest `dependencies: ["mqtt"]`, `quality_scale: legacy`, `codeowners: []`; docs page calls it a "Legacy integration", "community maintained"). Read in full (2026.9.4): it listens on `MATCH_ALL`, and for each event with `origin == local` (and not in `ignore_event`, and not its own MQTT publish call) publishes JSON `{"event_type", "event_data"}` to a configured `publish_topic`; on the `subscribe_topic` it parses JSON and re-fires the event locally with `origin=EventOrigin.remote`, rebuilding `State` objects for `state_changed` old/new state, and blocking `homeassistant_start/started/stop/close/final_write` events. The `origin != local` check is the loop guard. Events only: no service forwarding, no state-machine mirroring, no auth beyond MQTT broker, no schema/version negotiation observed. Configured via YAML only (`CONFIG_SCHEMA`, no config flow). This is the only in-core use of `EventOrigin.remote` for instance linking.
- Beyond that, searches and the community thread (community.home-assistant.io/t/multiple-ha-instances-now-possible/484637) point to the custom integration; I found no other official HA-to-HA feature (absence claim, not exhaustive over all 1509 integrations). The thread notes the mobile Companion app can hold multiple instances (client-side, not instance-to-instance) and Nabu Casa subscriptions are per instance. Matter multi-admin is a generic protocol, not an HA-to-HA feature, and I did not verify it here.
- `remote_homeassistant` (github.com/custom-components/remote_homeassistant, README on master): main instance connects to the remote's WebSocket API; remote states are populated into the main instance's state machine (optional `entity_prefix`, include/exclude filters, value filters); service calls on a remote object are forwarded to that instance; events forwardable by subscription; "proxy services" for non-entity services. Requirements/limits stated in README: "must be installed on both the main and remote instance"; on disconnect "all previously published states are removed again from the local state registry"; remote domains not loaded locally need `load_components` (else "Call service failed"); components like `hdmi_cec` need proxy services since "it is not possible to forward the service calls properly". Issues page (fetch-tool summary, March-Sept 2026): setup blocking startup when remote is offline (#383), "No remote entities or devices" (#390), remote `zone.home` conflicting with local `zone.home` (#380), breakage after HA updates. I did not open the individual issues.
- Consequence observed (mine): the remote state machine is merged into the local one, so entity_id namespace and startup ordering conflicts arise; the mechanism is code running inside both instances, connected over an authenticated WebSocket.

### 7. Typing

**Verified:**
- Type checker: mypy. Config is generated by hassfest from `.strict-typing` (script/hassfest/mypy_config.py); listed modules get strict flags (`disallow_untyped_defs`, `disallow_untyped_calls`, `check_untyped_defs`, ...). At 2026.9.4: 1509 component directories; `.strict-typing` has 632 `homeassistant.components...` lines (some wildcards; count is a rough indicator). "Strict typing is enabled by default for core files." Platinum quality-scale tier requires fully typed code. Development checklist: core integrations "should include complete type hints, tracked in the `.strict-typing` file."
- `ConfigEntry` is generic over its runtime payload: `class ConfigEntry[_DataT = Any]` with `runtime_data: _DataT` (config_entries.py:392-399); integrations define an alias like `type MyConfigEntry = ConfigEntry[MyData]`. Alias pattern verified: `type SunConfigEntry = ConfigEntry[Sun]` (components/sun/entity.py:37).
- `EventType[T]` / `EventStateChangedData` give typed event payloads for some core events (core.py, const.py:286). `hass.data` is typed via `HassKey[T]` keys, e.g. `DATA_RECORDER: HassKey[RecorderData] = HassKey("recorder")` (helpers/recorder.py:21).
- Dependency typing: none found. Dependencies are `dependencies`/`after_dependencies` string lists in JSON; the only cross-check is hassfest's AST import scan described in section 2. `hass.components.<name>` style access (dynamic) existed historically; hassfest still references it in docstring/comments ("Find usage of hass.components", dependencies.py) so treat its current status as unverified.
- Library requirement: protocol code must live in a PyPI library (dev docs api_lib_index), typed/tested libraries are separate from integrations.

### 8. Failure modes and criticisms

Documented in primary sources or observed in repo:
- **Shared environment.** Requirements for all integrations install into one Python environment with core constraints (`CONSTRAINT_FILE`, requirements.py:99). Docs tell custom integrations not to require anything core already requires. Conflicts (FAQ page above; issues secondary).
- **No stable plugin ABI.** Internals change monthly; custom integrations get log warnings while core ones raise (frame.py). Examples: `via_device`, `modbus.get_hub`, `DeviceEntry.config_entries` (dev blog).
- **Silent-ness of removals: contested.** A third-party article (trunetto.com, low quality; seen only as a search-result snippet, page never opened) claims removal of legacy template syntax made automations "silently fail". The primary community thread by the integration author says users got repair notifications 2025.12-2026.5 and a migration tool, and some users say they never saw them. Primary sources support "warned but many users missed it", not "no warning"; whether the failure at 2026.6 was silent for users who ignored repairs I could not verify.
- **Dependency semantics are loose.** `dependencies` does not guarantee config entries are set up; `after_dependencies` is order-only for configured integrations; static check exists only in hassfest, not at type level. Dependents fail if a dependency fails.
- **Setup blocking.** Timeouts per stage (`STAGE_1_TIMEOUT = 120`, `STAGE_2_TIMEOUT = 300`, bootstrap.py:146-147); remote_homeassistant issue #383 (offline remote blocks bootstrap, unverified in detail).
- **One flat state namespace.** `entity_id` = `domain.object_id`; remote_homeassistant issue #380 (`zone.home` collision).
- **Templates.** Jinja embedded in YAML: triggers can't use templates except via limited `trigger_variables`; blueprint inputs are not template variables; `limited` vs full template split; sandboxed with 256 KiB output cap. A broader body of user complaints exists (community threads) but I have not sampled it beyond search snippets.
- **Unsourced but common criticisms (not verified, omitted deliberately):** performance of the recorder/state_changed firehose, HACS-related update breakage rates. I found no primary data.

## Mechanisms relevant to the stated direction

Observations only.

- *Library with chainable plugin registration; team features as ordinary plugins.* HA has no chainable registration: integrations are discovered by directory and manifest, and enabled by config or config entries. Core integrations (calendar-like, `sun`, automation) use the same loader and the same `hass` object as custom ones; the built-in vs custom distinction is manifest rules, review/CI, and deprecation-report behaviour, not different APIs. A `custom_components` directory can shadow a built-in one.
- *Plugins fire events; dependencies detectable through types.* Events are strings (optionally `EventType[T]` typed for some) on a single bus with `MATCH_ALL`; event types are capped at 64 chars. Dependencies are JSON string lists resolved at runtime (`dependencies` = must be set up first, failure propagates; `after_dependencies` = order only if configured), and checked against actual imports only by an AST scan in CI (hassfest). No type-level expression of inter-integration dependencies exists; `ConfigEntry[T]` types only an integration's own runtime data.
- *HTTP backend and optional UI.* REST and WebSocket APIs and the frontend are themselves integrations on the same `hass` object; the frontend is a client of the same WebSocket API, and integrations can register their own websocket commands and custom panels. The docs give no stability guarantee for REST.
- *Non-coders fire pre-made functions with changed parameters.* Actions (services) are registered with a schema and optional `services.yaml` description so the UI can render forms; scripts wrap action sequences; blueprints parameterise YAML with `!input` and selectors, with the limitation that inputs are YAML-tag substitutions, not template variables. `call_service` accepts a `return_response` flag and services declare `SupportsResponse` = `NONE` (default), `OPTIONAL` or `ONLY` (core.py:2539-2547 and dev docs).
- *Federation: servers own containers, exchange only data and events, never code.* HA's closest official piece is `mqtt_eventstream` (legacy status): events-only JSON over an MQTT broker, re-fired locally with `EventOrigin.remote`, with a loop guard on `origin` and a block-list of lifecycle events; YAML-configured, no service forwarding. Otherwise no official equivalent. The community approach (`remote_homeassistant`, a separate path) requires the same component code on both sides, mirrors remote states into the local state machine (removed on disconnect), and forwards service calls; observed problems are namespace collisions, startup blocking, and version breakage. `EventOrigin.remote` exists in core and is set by the REST event endpoint, the mobile_app fire_event webhook and mqtt_eventstream.
